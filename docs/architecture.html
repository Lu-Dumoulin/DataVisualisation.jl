The dashboard is a Julia program that drives a web page. All decisions are taken in Julia; the browser only shows widgets and figures and reports what the user does. Bonito keeps observables (values that notify listeners when they change) in sync between the two sides over a WebSocket; WGLMakie turns Makie figures into WebGL canvases on the page.

1. The big picture — layers

The separation that matters: App.jl only connects (a listener never does work itself, it schedules it), State.jl decides (what to load, whether a figure can be updated in place), and Plotting.jl computes from a folder and a PlotConfig — a plain snapshot of every setting, built in one place (plot_config(d)). Rendering never reads a widget directly.

2. Start-up: from explor_app to the first figure

  • Once per process: DataWorkspace(csv, ext) reads DF.csv, finds the varying parameters, their value lists and ranges, the run folders, the number of frames and the field keys. It is shared by every session.
  • Once per browser tab: Bonito calls the App handler, which builds a fresh Dashboard — two tabs never share widgets or figures.
  • Precompilation (precompile.jl) runs steps ②–⑦ on a tiny generated ensemble when the package is installed, so the first real page takes ≈3 s instead of ≈10 s. It skips connect! and the player: their background tasks would block precompilation.

5. The Debouncer — why nothing ever queues up

Because f always reads the current selections, a burst of 50 slider events while one render runs gives one more render with the last value — never 50 queued renders, and the final position is never lost. busy(renderer) (active or pending) is also what the player waits on.

Nothing is cached across frames in data mode: each frame is read from disk (only the fields in use), reduced, and dropped when the next one arrives. Memory therefore stays at about one frame, whatever the run length — except in the 1D whole-run views, which hold the run's profiles by design.

8. Clicks and drags on a time line

Why the rebuild delay exists. A rebuild replaces the canvas. Replacing it again before the browser has finished setting the previous one up makes WGLMakie throw (setup_scene_init on a removed canvas) and breaks the page until a refresh — this is what a fast drag of the arrow size did before it became an in-place update.

10. Rules that keep it working

Listeners schedule, they don't work. Writes to browser-synced observables from inside a listener go through @async or a Debouncer; writing while Bonito is still processing the current message causes "notify on null".
Julia → browser widget writes use set_value! (index), never .value alone.
Listeners use on_change: the browser echoes every value Julia sets; without the filter each animation frame would render twice.
Rebuilding the top bar adjusts selections silently (setfield!(obs, :val, …), no notify) and is always followed by one schedule!(renderer).
A run change renders once: reload_keys! (fields, slices, menus) first, then the render — never a render on the path change and another on the key change.
Anything that can change during playback must be an observable input of the figure (data, style, frame marker), not part of layout_key — otherwise each change rebuilds the canvas. Anything in layout_key goes through settle_before_rebuild.
Makie attributes that follow data are passed as observables when the plot is created (e.g. Axis(…; title=obs)); assigning an observable afterwards (ax.title = obs) is an error.
Nothing that spawns tasks goes into the precompile workload (connect!, the player): precompilation would wait for them forever.

Testing

  • julia --project=. -e 'using Pkg; Pkg.test()' — 642 tests, ≈1 min, also run by GitHub Actions CI on every push. Pure functions are tested directly; the app is tested headlessly with DV.dashboard(ws, Bonito.Session()): setting a widget's value fires the same listeners a browser would.
  • julia dev/browser_check.jl <scenario> <DF.csv> <outdir> [fps] — the real page in headless Chrome through the DevTools protocol: browser errors, frames per second, rebuilt canvases, screenshots. Scenarios: load, polar, play, png-play, 3d, 1d, drag, hover, range. It finds what the Julia tests cannot see (index/value desync, stuck spinners, WebGL errors).
  • julia demo.jl 1|2|3 — the generated ensemble (shapes, orders, anchorings) to try a change by eye.
